# TC 명세 양식

**TC 는 사람이 씁니다.** 무엇을 검증할지는 화면과 업무를 아는 사람만 정할 수 있고,
그것 없이 쓴 테스트는 "돌아가긴 하는데 무엇을 지켜주는지 모르는 코드" 가 됩니다.

이 문서는 [가이드 1장 0단계](AUTOMATION_GUIDE.md#0단계--대상-정하기-5분)의 확장판입니다.
0단계 메모로 충분한 경우가 많고, 아래 양식은 **TC 를 여러 개 모아 문서로 남길 때**
쓰세요. 항목 이름은 0단계와 같습니다.

---

## 양식

TC 하나당 이 블록 하나입니다. 그대로 복사해서 채우세요.

```markdown
### TC001 로그인 — 정상 계정으로 로그인하면 대시보드가 보인다

- **업무 영역**: 로그인
- **실행 집합**: smoke
- **사전조건**: 활성 상태의 일반 사용자 계정 (비로그인 상태에서 시작)
- **테스트 데이터**: config 의 user 계정
- **절차**
  1. 로그인 화면 접속
  2. 아이디 / 비밀번호 입력 후 로그인 클릭
  3. 대시보드로 이동했는지 확인
- **기대결과**: 대시보드 제목 "대시보드" 가 화면에 보인다
```

## 항목이 코드의 어디로 가는가

이 대응이 양식을 쓰는 이유입니다. **빈칸이 있으면 그 자리가 코드에서 비어버립니다.**

| 명세서 항목 | 코드에서 되는 것 | 비고 |
|---|---|---|
| 제목 (`—` 뒤 문장) | docstring 첫 줄 | **리포트 제목이 됩니다.** 한글로 씁니다 |
| TC ID | `@pytest.mark.tc_id("TC001")` | 화면·기능별로 앞자리를 나눠두면 나중에 찾기 쉽습니다 |
| 업무 영역 | `@pytest.mark.login` 등 | 새 marker 는 `pytest.ini` 에 등록해야 합니다 (`--strict-markers`) |
| 실행 집합 | `@pytest.mark.smoke` / `regression` / `e2e` | 아래 「실행 집합 고르기」 참고 |
| 사전조건 | fixture 선택 (`page` / `role_page("user")`) | 로그인이 필요하면 `role_page` → `fixtures/auth.py::perform_login` 구현 필요 |
| 절차 1줄 | `with test_step("…"):` 1개 | **한 줄 = Step 하나.** 리포트에 이 단위로 찍힙니다 |
| 기대결과 | `expect(...)` 단정 | 여기가 비면 "클릭만 하고 끝나는 테스트" 가 됩니다 |
| 테스트 데이터 | 코드에서 생성 또는 `data/*.yaml` | 케이스가 여러 개면 yaml 로 빼서 파라미터화 |

### 실행 집합 고르기

| 집합 | 무엇을 넣나 | 주의 |
|---|---|---|
| `smoke` | 배포 직후 가장 먼저 볼 최소 항목 | 자주 도는 집합이라 **데이터를 만드는 테스트는 피하세요** |
| `regression` | 회귀 전체. 대부분의 TC 가 여기 | |
| `e2e` | 여러 화면에 걸친 업무 흐름 | 테스트 간 순서 의존이 허용되는 유일한 집합 |

## 쓸 때 지켜야 하는 것 3가지

### ① 기대결과는 "화면에서 눈으로 보이는 것" 으로

| ✗ 이건 TC 가 아님 | ✓ 이렇게 |
|---|---|
| 정상적으로 등록된다 | 목록 최상단에 입력한 이름이 보인다 |
| 에러 없이 저장된다 | 상세 화면 제목이 입력값과 같다 |
| 유효성 검사가 동작한다 | 입력칸 아래에 "필수 입력 항목입니다" 가 표시된다 |
| 버튼이 잘 동작한다 | URL 이 `/order/{번호}` 로 바뀐다 |

판정 가능한 형태는 결국 넷 중 하나입니다 — **문구 / 개수 / URL / 노출 여부.**
화면 문구는 **실제 문구를 따옴표로 그대로** 적으세요. 모르면 `(문구 확인 필요)` 라고
적어두면 됩니다. 지어낸 문구로 코드를 쓰면 그 테스트는 반드시 깨집니다.

### ② 절차는 "사람이 화면에서 하는 행동 한 덩어리" 단위로

```text
✗ 너무 잘게                  ✓ 적당히
1. 아이디 칸 클릭             1. 로그인 화면 접속
2. 아이디 입력                2. 아이디 / 비밀번호 입력 후 로그인
3. 비밀번호 칸 클릭           3. 대시보드 이동 확인
4. 비밀번호 입력
5. 로그인 버튼 클릭
```

3~6줄이 적당합니다. **10줄을 넘으면 TC 가 너무 큰 것**이니 나누세요
([안티패턴 ⑩](AUTOMATION_GUIDE.md#4-안티패턴-도감)).

### ③ Locator 는 적지 않아도 됩니다

`data-testid` 값이나 CSS 셀렉터는 **코드를 쓰는 쪽 몫**입니다 (실제 화면에서 확보).
명세서에는 **화면에 보이는 이름**으로 적으세요 — "프로젝트명 입력칸", "등록 버튼",
"필수(\*) 표시된 항목 전부" 로 충분합니다.

## TC 를 몇 개로 나눌까

**TC 하나 = 목적 하나** 입니다. 목적이 둘이면 TC 를 나눕니다.

기대결과가 2개인 것은 괜찮습니다 — **하나의 목적을 뒷받침하는 확인**이라면요.
"로그인됐다" 를 URL 과 헤더 버튼 두 가지로 확인하는 것은 목적 하나입니다.
반면 "로그인된다 + 최근 주문이 보인다" 는 목적이 둘이므로 나눠야 합니다.

같은 절차에 입력값만 다른 케이스가 여러 개면 **TC 를 늘리지 말고 데이터로 빼세요.**

```markdown
- **테스트 데이터**: `data/login_cases.yaml` 의 `invalid_email_cases`
  | id | 입력 | 기대 문구 |
  |---|---|---|
  | no-at | `userexample.com` | 이메일이 올바르지 않습니다. |
  | no-domain | `user@` | 이메일이 올바르지 않습니다. |
```

코드는 한 벌이고 yaml 만 늘어납니다 (`tests/example/test_example.py` 의
`parametrize` + `load_data` 참고).

## 넘기기 전 체크리스트

TC 를 코드로 옮기기 전에 이 4개를 확인하세요. 하나라도 걸리면 아직 못 씁니다.

- [ ] 기대결과가 **화면에서 눈으로 확인 가능한 것 하나**인가
- [ ] 화면 문구를 **실제 문구 그대로** 적었는가 (모르면 `(확인 필요)` 표시)
- [ ] 이 TC 가 **다른 테스트가 만든 데이터에 기대지 않는가**
- [ ] 데이터를 만드는 TC 라면 **이름이 유니크한가** (병렬 실행에서 충돌합니다)

## 채워진 예시

이 저장소에 실제로 있는 테스트를 역으로 명세서로 쓴 것입니다.

### SMK001 Todo — 메인 화면 접속 및 기본 요소 노출

- **업무 영역**: Todo
- **실행 집합**: smoke
- **사전조건**: 없음
- **테스트 데이터**: 없음
- **절차**
  1. 메인 화면 접속
  2. 제목과 입력창 확인
- **기대결과**: 제목과 할 일 입력창이 화면에 보인다

→ `tests/smoke/test_smoke_todo.py::test_home_page_opens`
절차 2줄이 `test_step` 2개, 제목이 docstring, 기대결과가 `expect` 2줄입니다.
